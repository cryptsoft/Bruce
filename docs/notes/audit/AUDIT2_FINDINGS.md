## #1 [HIGH/bug/rust] GetAssertion still derives uv_present from field presence (incomplete H4 fix) -- credProtect-3 bypass and with_uv hmac-secret disclosure on PIN-less device
- **Where:** `crates/firmware/src/ctap2.rs`:2298
- **What:** H4 was remediated for MakeCredential by introducing `uv_happened` (ctap2.rs:1463), initialised false and set true ONLY inside the `if store.pin.pin_set != 0` block after a successful verify_pin_uv_auth_param (line 1539). The GetAssertion path was NOT given the same treatment: at line 2298 `let uv_present = pin_uv_auth_param.is_some() && pin_uv_auth_protocol.is_some();` is computed purely structurally and OUTSIDE the pin_set guard. The pinUvAuthParam verification block (lines 2248-2292) is entered only when store.pin.pin_set != 0; when no PIN is set it is skipped entirely, yet uv_present is still computed from mere field presence. H4's own fix text mandates: 'Derive uv_present/uv_happened only from a boolean set inside a verification path that actually succeeded, never from field presence' and 'When pinUvAuthParam is present but no PIN is set, return CTAP2_ERR_PIN_NOT_SET (0x35)'. Neither is done on GetAssertion. uv_present then feeds: the credProtect-3 gates at lines 2414, 2444, 2551 (`cred_protect == 3 && !uv_present`), the credProtect-2 gate at 2555, the with_uv vs no_uv cred_random selection for hmac-secret (passed at line 2587 into hmac_secret_compute_output), and the AUTHDATA_FLAG_UV bit (lines 2603-2605).
- **Fix:** Replace the structural computation at line 2298 with a boolean set true only inside the verified branch, exactly as MakeCredential does with uv_happened: initialise `let mut uv_present = false;` before line 2248 and set `uv_present = true;` only after the successful verify_pin_uv_auth_param at the end of the pin_set!=0 block (after line 2291). Additionally, when pinUvAuthParam is present but store.pin.pin_set == 0, return CTAP2_ERR_PIN_NOT_SET (0x35) per CTAP 2.1, matching the H4 fix intent. Apply the same audit to GetNextAssertion, which inherits uv_present from the stashed AssertionIterState (line 2468) -- it is correct there only if the originating GetAssertion computes it correctly.

## #2 [MEDIUM/bug/rust] MakeCredential persists the resident credential to flash before the cancellable hybrid sign -- CTAPHID_CANCEL leaves an orphan active credential
- **Where:** `crates/firmware/src/ctap2.rs`:1998 (store.insert) vs 2122-2145 (sign + cancel return)
- **What:** In emit_make_credential the resident-credential commit happens BEFORE the cancellable hybrid sign. At line 1998 `store.insert(cred)` runs, and CredStore::insert calls `self.persist()` (ctap2.rs:493) which writes the slot to flash with state=STATE_ACTIVE. Only afterward, at line 2122-2124, does `opensk_hybrid_sign(...)` run the multi-second ML-DSA sign that pumps KEEPALIVE and watches for CTAPHID_CANCEL. When the host dismisses the WebAuthn prompt, opensk_hybrid_sign sets sign_cancelled=true and the handler returns CTAP2_ERR_KEEPALIVE_CANCEL at line 2142-2144 WITHOUT removing or tombstoning the slot it just persisted. There is no rollback/delete between the insert and the cancel return (verified: only sign_cancelled handling, no STATE_/delete in 1977-2145). Net effect: a cancelled hybrid MakeCredential leaves a fully active, discoverable resident credential permanently in flash. This is the opposite of GetAssertion's correct ordering, where store.bump_counter (line 2676) runs AFTER the cancel check (line 2669), so a cancelled GetAssertion never persists. The L15/cancel remediation was applied symmetrically to the three sign call-sites but the MakeCredential persist was not moved past the cancel point.
- **Fix:** Defer the resident-credential commit until after the cancel check, mirroring GetAssertion: move the `if rk_requested { ... store.insert(cred) ... }` block (lines 1977-2002) to after the `if sign_cancelled { return; }` guard at line 2142-2145. The credential_id, authData, and COSE key are already computed independently of the slot, so the insert only needs the final-sig path to have completed (not cancelled) before persisting. Ensure KEY_STORE_FULL is still reported (it can now be reported post-sign, which is acceptable since no signature is returned on that error).

## #3 [MEDIUM/bug/rust] changePIN consumes a PIN retry (and can permanently lock the device) when the current PIN is CORRECT but the new PIN fails the length/decrypt check
- **Where:** `crates/firmware/src/client_pin.rs`:971-1021 (early returns at 1007-1008 and 1011-1015)
- **What:** In sub_change_pin the persistent retries_left is decremented and persisted at line 971-972 BEFORE the current-PIN comparison. On a CORRECT current PIN the ct_eq at line 992 passes, the volatile counter is cleared at line 1006, but retries_left is only restored to PIN_MAX_RETRIES at line 1021 -- AFTER two further fallible steps: (a) decrypting the new PIN (line 1007; on structural failure returns ERR_INVALID_PARAM at 1008 without restoring retries) and (b) the actual_len < min_pin_length policy check (line 1012; returns ERR_PIN_POLICY_VIOLATION at 1014 without restoring retries). So a request that authenticates the current PIN correctly but supplies a too-short or undecryptable new PIN permanently consumes one of the 8 retries. The C port does NOT have this bug: c/firmware/src/client_pin.c verify_pin_hash_enc restores retries to PIN_MAX_RETRIES (line 269) the instant the current PIN matches, before the new-PIN decode/policy checks (lines 310-315) -- so this is a Rust-only divergence introduced by the reordered reset.
- **Fix:** Restore persistent.retries_left = PIN_MAX_RETRIES and persist it immediately after the current-PIN ct_eq succeeds (right after session.clear_pin_failures() at line 1006), before decrypting/validating the new PIN -- matching the C port's verify_pin_hash_enc ordering. The new-PIN policy/decrypt failures should then return their errors without having consumed a retry.

## #4 [MEDIUM/bug/c] C port leaves the PIN-protocol shared secret (AES/HMAC keys) un-wiped on the stack in all three ClientPIN handlers -- incomplete M2 remediation
- **Where:** `c/firmware/src/client_pin.c`:sub_set_pin 194-219; sub_change_pin 290-324; sub_get_token 340-392
- **What:** The M2 fix added pqf_cleanse() for pin[], full[], got[], stored[] but the pin_shared_secret_t ss local -- which holds 64 bytes of live key material (aes_key[32] + hmac_key[32]; see pin_protocol.h:37-41, v1: SHA-256(ECDH.Z), v2: HKDF-derived AES/HMAC keys) -- is never cleansed on ANY path of sub_set_pin (declared line 194), sub_change_pin (line 290), or sub_get_token (line 340, used to encrypt the token at line 382 then function returns at 391 without wiping). The project's own pqf_cleanse.h header explicitly lists 'shared-secret/key material' as a buffer that must be cleansed, and the Rust port wipes the equivalent SharedSecret on every exit path via secret.cleanse(). So the C side diverges from both the documented M2 discipline and the Rust port: the per-attempt AES/HMAC keys derived from the ECDH handshake remain resident on the stack after each ClientPIN subcommand returns.
- **Fix:** Add pqf_cleanse(&ss, sizeof ss) on every return path of sub_set_pin, sub_change_pin, and sub_get_token (or wrap with a single cleanup label / goto out pattern), mirroring the Rust secret.cleanse() calls.

## #5 [MEDIUM/bug/c] C port has no per-power-cycle consecutive-failure PIN lockout (ERR_PIN_AUTH_BLOCKED 0x34) -- L2 fixed only in Rust despite being filed 'both ports'
- **Where:** `c/firmware/src/client_pin.c`:verify_pin_hash_enc 227-271 (no 0x34 path); whole file has no consecutive-failure counter
- **What:** AUDIT_FINDINGS L2 (marked [x] fixed, scope 'Rust+C', fix note 'Coordinate both ports') and CTAP 2.1 sec. 6.5.5.6 require a volatile counter that blocks PIN entry with CTAP2_ERR_PIN_AUTH_BLOCKED (0x34) after MAX_CONSECUTIVE_PIN_FAILURES (3) wrong PINs in one power cycle, in addition to the persistent 8-retry counter. The Rust port now implements this (client_pin.rs:57,170,196-209,941-944,1073-1076 with note_pin_failure/clear_pin_failures), but the C port's verify_pin_hash_enc gates only on the persistent retries==0 (line 231-232) and there is no consecutive-failure counter or 0x34 return anywhere in c/firmware/src/client_pin.c (grep for 0x34/PIN_AUTH_BLOCKED/consecutive returns nothing). The CHANGELOG scoped the L2 fix to '(Rust)' only, leaving the C remediation incomplete.
- **Fix:** Add a volatile static consecutive-failure counter to client_pin.c, increment it on each wrong-PIN branch of verify_pin_hash_enc, return CTAP2_ERR_PIN_AUTH_BLOCKED once it reaches 3 (checked in sub_change_pin and sub_get_token before spending a persistent retry), clear it on a correct PIN and on Reset, mirroring the Rust PinSession lockout.

## #6 [MEDIUM/bug/rust] Cancelled hybrid MakeCredential leaves the resident credential persisted to flash (slot leak + silent overwrite of an existing passkey)
- **Where:** `crates/firmware/src/ctap2.rs`:1998-2002 (insert+persist) vs 2122-2145 (sign + cancel return)
- **What:** In emit_make_credential the resident-credential branch calls store.insert(cred) at line 1998, and CredStore::insert (ctap2.rs:438-495) calls self.persist() at line 493 -- committing the new StoredCredential to the credential flash sector immediately. The hybrid ML-DSA sign runs AFTERWARD via opensk_hybrid_sign at line 2124. If the host sends CTAPHID_CANCEL during the multi-second sign, the new L15 path sets sign_cancelled and emit_make_credential returns CTAP2_ERR_KEEPALIVE_CANCEL at lines 2142-2145 WITHOUT rolling back the already-persisted slot. The host receives KEEPALIVE_CANCEL and believes no credential was created, but a resident credential now occupies a finite flash slot. Worse: insert() de-dups by (rp_id_hash, user.id) and overwrites the matching slot IN PLACE (lines 443-468, then persist at 493). So a re-registration of an EXISTING account that is then cancelled mid-sign has already destroyed the user's prior passkey for that account (its credential_id/counter were overwritten and flashed) even though the ceremony was reported cancelled. This asymmetry is specific to MakeCredential: GetNextAssertion (cancel check at 1111 precedes bump_counter at 1115) and GetAssertion (cancel check 2669 precedes bump_counter 2676) both persist only AFTER the cancel check, so they are correct. Only the MakeCredential persist (insert) happens before the sign/cancel check.
- **Fix:** Defer the resident-credential insert until AFTER the sign succeeds and the cancel check passes -- move the store.insert(cred)/KEY_STORE_FULL block (1977-2002) to just before building the response (after line 2145). Alternatively perform a slot reservation that is committed only post-sign, and on the dedup-overwrite case snapshot the prior slot and restore it if sign_cancelled. Either way no flash mutation must survive a KEEPALIVE_CANCEL return.

## #7 [MEDIUM/bug/c] C CredentialManagement enumeration iterators are not bound to the originating channel -- cross-channel credential-metadata disclosure (M12 parity gap)
- **Where:** `c/firmware/src/credential_management.c`:56-73, 200-211, 229-239
- **What:** The newly written C port stores the enumerateRPs / enumerateCredentials iterator state in file-static singletons `s_rp_iter` / `s_cred_iter` with NO channel-id field and no per-session ownership (compare the Rust port which now carries `_cid` and compares `state._cid == cid` in both GetNext handlers -- credential_management.rs:386, 474). The dispatcher only resets the iterators on a *non*-CredentialManagement command (ctap2.c:1291-1292), so two distinct HID channels that each issue only authenticatorCredentialManagement (0x0A) commands share the same iterator. Channel A issues enumerateCredentialsBegin/enumerateRPsBegin (after its own valid PIN/UV auth); channel B then issues enumerateCredentialsGetNextCredential / enumerateRPsGetNextRP -- which reauthenticate nothing (needs_auth is false for GetNext, line 284-285) -- and reads/advances channel A's iterator, harvesting resident-credential metadata (user.id, user.name, displayName, credentialID, rpIDHash) without ever holding the credMgmt-permissioned token. CTAP 2.1 sec. 6.8/sec. 11.2 require stateful commands to be bound to the originating session.
- **Fix:** Add a `uint8_t cid[4]` (or channel handle) to both iterator structs, capture it at Begin, and have credential_management_handle receive the originating CID and refuse (drop the iterator, return ERR_NOT_ALLOWED) when the GetNext CID does not match. Mirror the Rust `_cid` binding.

## #8 [MEDIUM/bug/rust] GetNextAssertion iterator is not bound to its originating HID channel (stored _cid never checked)
- **Where:** `crates/firmware/src/ctap2.rs`:943 (dispatch), 1003-1028 (emit_get_next_assertion), 224 + 2471 (_cid stored but dead)
- **What:** AssertionIterState carries a `_cid: [u8;4]` field that is populated at GetAssertion time (ctap2.rs:2471 `_cid: cid`), mirroring the channel-binding the credentialManagement iterators use. But the GetNextAssertion handler is dispatched WITHOUT the channel id -- `CTAP2_GET_NEXT_ASSERTION => emit_get_next_assertion(session, store, host, now_us, &mut out)` (ctap2.rs:943) -- and `emit_get_next_assertion` (signature at 1003-1009) never receives or compares `cid`. The only guard on a GetNext is the 30s deadline (1014). Contrast the CM path, which IS wired with `cid` (ctap2.rs:947) and whose GetNext handlers correctly enforce `s._cid == cid` (credential_management.rs:386 and :474). So the assertion iterator's `_cid` is assigned-but-dead. This is the exact 'claimed-but-unimplemented channel binding' defect the remediated M12 fixed for the CM iterators, left unfixed for the assertion iterator.
- **Fix:** Plumb `cid` into emit_get_next_assertion (as the CM handlers already do) and, in the snapshot block at ctap2.rs:1012-1029, drop the iterator and return ERR_NOT_ALLOWED (0x30) when `iter._cid != cid`. Note `_cid` is `[u8;4]` (cid.to_be_bytes()) while the CTAPHID cid is u32 -- compare consistently (the CM path stores/compares the [u8;4] form, so pass `cid.to_be_bytes()` through identically).

## #9 [MEDIUM/bug/rust] Cancelled hybrid rk=true MakeCredential persists a resident credential the host believes was never created (L15+M15 interaction)
- **Where:** `crates/firmware/src/ctap2.rs`:1977-2002 (resident insert+persist), 2122-2145 (hybrid sign then sign_cancelled -> KEEPALIVE_CANCEL)
- **What:** In emit_make_credential the resident credential is inserted and committed to flash via store.insert(cred) (line 1998, which calls CredStore::insert -> self.persist() at ctap2.rs:493) BEFORE the attestation signature is produced. For hybrid (ML-DSA) credentials the signature runs on core 1 via opensk_hybrid_sign, which is cancellable: if the host sends CTAPHID_CANCEL during the ~1.5-2 s sign, sign_cancelled is set and the handler returns CTAP2_ERR_KEEPALIVE_CANCEL at line 2142-2145 -- but the resident credential is already persisted and is never rolled back. emit_get_assertion was written to avoid this (it checks sign_cancelled at line 2669 BEFORE bump_counter at line 2676), but MakeCredential does the persisting state-change before the cancellable sign. Worse, when insert() takes the (rp_id_hash, user.id) dedup-overwrite path (ctap2.rs:443-448), the prior credential for that account has already been irreversibly overwritten in flash before the cancel.
- **Fix:** Defer the resident store.insert()/persist() until AFTER the sign completes and the sign_cancelled check passes, or capture the prior slot contents and restore them (re-persist) on the cancelled path. Order MakeCredential state-changing flash writes after the cancellable operation, matching GetAssertion's check-cancel-before-bump_counter ordering.

## #10 [MEDIUM/bug/cross] largeBlobs write pinUvAuthParam layout disagrees with both firmware ports -- every PIN-protected write fails auth
- **Where:** `crates/ctaphid-client/src/ctap2/large_blobs.rs`:114-127
- **What:** write_fragment() builds the pinUvAuthParam HMAC input as `[0xff;32] || 0x0c (CMD_LARGE_BLOBS) || [0u8;4] || SHA-256(offset_le_u32 || fragment)` -- 69 bytes, with the offset folded INTO the SHA-256 input and four zero bytes where the LE offset should be, and NO 0x02 discriminant byte. Both firmware ports verify over a different message: `[0xff;32] || 0x0c || 0x02 || offset(4 LE) || SHA-256(set)` (70 bytes). See crates/firmware/src/large_blobs.rs pin_auth_message() lines 167-176 (`buf.push(0x0C); buf.push(0x02); buf.extend_from_slice(&offset.to_le_bytes()); ... Sha256::digest(set_data)`) and the identical C layout at c/firmware/src/large_blobs.c lines 209-216 (`msg[32]=0x0c; msg[33]=0x02; msg[34..38]=offset LE; sha256(set, ..., msg+38)`). The two HMAC inputs differ in three independent ways (missing 0x02 byte, offset placement, and what bytes feed the SHA), so the host-computed tag can never equal the firmware-computed tag.
- **Fix:** Match the firmware byte-for-byte: build auth_input as `[0xff;32] || CMD_LARGE_BLOBS || 0x02 || offset.to_le_bytes() || SHA-256(fragment)`. Drop the four zero bytes and the offset-in-SHA; add the 0x02 byte and place the 4-byte LE offset as a separate field, hashing only `fragment`. (Note both firmware ports use 0x0c 0x02 where CTAP 2.1 sec. 6.10.5 nominally specifies 0x0c 0x00; if strict spec conformance is also wanted, change all three sites together -- but the immediate parity bug is the host diverging from the firmware it must interoperate with.)

## #11 [MEDIUM/bug/rust] AuthData::parse fails on any MakeCredential authData carrying extensions (ED flag) -- scan_cbor_item_length rejects trailing bytes
- **Where:** `crates/ctaphid-client/src/session.rs`:283-302
- **What:** scan_cbor_item_length() is meant to measure just the COSE_Key item inside attestedCredentialData and leave following extension bytes alone. It calls `pqf_cbor::decode(buf)` (line 289), but pqf_cbor::decode is the whole-buffer decoder that returns Error::Trailing whenever bytes remain after the first item (crates/cbor/src/lib.rs:557-559). When the firmware sets the ED flag (0x80), authData is `... || COSE_Key || extensions_map`, so the `remainder` slice passed here is COSE_Key followed by the extensions map. decode() therefore returns Err(Trailing), which the `?` on line 289-290 turns into Err(Error::Decode(...)) and propagates out of AuthData::parse -- BEFORE the non-canonical fallback at lines 293-298 can run. Verified empirically: encoding a COSE_Key map then appending `{"credProtect":2}` and calling pqf_cbor::decode returns Error::Trailing (cose_len=77, total=91).
- **Fix:** Don't use the whole-buffer decoder for a sub-item measurement. Either (a) add/extend pqf_cbor with a decode-prefix variant that returns (Value, bytes_consumed) and stops after one item, or (b) hand-scan the COSE_Key length. Simplest in-place fix: catch Error::Trailing specifically and re-run against successively shorter prefixes, or better, expose the Cursor position from a one-item decode. The existing canonical-reencode trick can then run on just the consumed prefix to confirm the boundary.

## #12 [LOW/bug/rust] GetNextAssertion pops the iterator index before the cancellable hybrid sign -- cancel loses the credential from the iterator
- **Where:** `crates/firmware/src/ctap2.rs`:1026 (remove(0)) / 1038 (iter drop) vs 1111 (cancel return)
- **What:** emit_get_next_assertion pops the next slot index from session.assertion_iter.remaining_slot_idxs via remove(0) at line 1026, and may drop the whole iterator at line 1038, BEFORE the cancellable hybrid sign at line 1081. If the host sends CTAPHID_CANCEL during a hybrid sign, the handler returns CTAP2_ERR_KEEPALIVE_CANCEL at line 1111-1113, but the iterator state has already been mutated: the popped credential is gone and (if it was the last one) the iterator has been dropped. A subsequent GetNextAssertion cannot re-fetch the credential the user cancelled on, and may instead return ERR_NOT_ALLOWED (0x30) for the rest of a multi-credential picker. Unlike the MakeCredential case this leaves no persistent flash state (no bump_counter runs on cancel, which is correct), so impact is limited to the in-RAM iterator for the current ceremony.
- **Fix:** Either (a) snapshot the index without removing it, and only commit the remove(0)/iterator-drop after the `if sign_cancelled { return; }` check; or (b) on cancel, push the popped index back to the front of remaining_slot_idxs and restore the iterator before returning KEEPALIVE_CANCEL. Option (a) mirrors the recommended MakeCredential fix (commit state only after the sign is known not to be cancelled).

## #13 [LOW/bug/both] forcePINChange (X13) is surfaced in getInfo but never enforced -- getPinToken / getPinUvAuthToken still succeed while a forced change is pending
- **Where:** `crates/firmware/src/client_pin.rs`:do_get_pin_token 1054-1116 (no force_pin_change gate); c/firmware/src/client_pin.c sub_get_token 329-392 (same)
- **What:** X13 adds a persistent force_pin_change flag, sets it from authenticatorConfig setMinPINLength forceChangePin (authenticator_config.rs:290), surfaces it as getInfo 0x0C forcePINChange (ctap2.rs:1347), and clears it on a successful changePIN (ctap2.rs:1200-1202). But the flag is purely advisory: neither port consults force_pin_change inside do_get_pin_token / sub_get_token, so getPinToken (0x05) and getPinUvAuthTokenUsingPinWithPermissions (0x09) still mint usable tokens while a forced change is outstanding. CTAP 2.1 sec. 6.5.5.7.2 requires the authenticator to refuse getPinUvAuthToken with CTAP2_ERR_PIN_POLICY_VIOLATION (0x37) when forcePINChange is set, so the host cannot proceed without first running changePIN. - **Fix:** In do_get_pin_token (Rust) and sub_get_token (C), after the pin_set/retries/lockout checks, return ERR_PIN_POLICY_VIOLATION (0x37) when the store's force_pin_change flag is set, so only changePIN can proceed until the flag is cleared. This requires threading the force_pin_change state into the PIN layer (it currently lives only on CredStore).

## #14 [LOW/bug/rust] largeBlobKey never returned on GetAssertion for non-resident credentials (Rust gates on the flash slot, not the credentialID)
- **Where:** `crates/firmware/src/ctap2.rs`:2755 (gate); 2510-2540 (cred_large_blob_key bound to slot, None branch=false); 1996 + 2152-2173 (MakeCred accepts + returns it for rk=false)
- **What:** The L11 largeBlobKey gating in the Rust port keys off the per-slot StoredCredential.large_blob_key flag (read at line 2526, defaulted to `false` at line 2540 for the `cred_idx == None` non-resident branch). The Rust credentialID plaintext does NOT carry a largeBlobKey bit (credential_id.rs reserves [97..112] as zero). MakeCredential, however, accepts `largeBlobKey` independently of `rk` (large_blob_key_requested is set regardless of rk_requested) and returns the 32-byte key at response key 0x05 even for a non-resident (rk=false) registration (lines 2152-2173). On the subsequent GetAssertion the credential is presented via allowList and has no flash slot, so cred_large_blob_key is forced false and the gate at line 2755 is never taken -- the key is silently omitted from response key 0x07. The C port does this correctly: it stores the minted-with-largeBlobKey bit in the credentialID plaintext (credential.c plain[97], CRED_FLAG_LARGE_BLOB_KEY) and gates on `src.large_blob_key` (ctap2.c:1105), which works for non-resident creds. So this is both a spec-feature break and an undocumented cross-port behavioral divergence.
- **Fix:** Carry the largeBlobKey flag in the credentialID plaintext (mirror the C port's plain[97] bit) and gate GetAssertion on `source.large_blob_key` from the decrypted credentialID rather than on the flash slot, so it works for resident and non-resident credentials identically. Add the field to CredentialSource and have encrypt/decrypt round-trip it. Alternatively, reject `largeBlobKey` on rk=false MakeCredential so the RP is never told it is supported when it cannot be honored. Coordinate the two ports.

## #15 [LOW/bug/cross] Resident-credential capacity diverged across ports (Rust=6, C=8) after the v11/v12 slot growth; C's parity-justification comment is stale and wrong
- **Where:** `c/firmware/src/resident_store.h:56-62 (stale claim); crates/firmware/src/flash_store.rs:404,410 (MAX_SLOTS); flash_store.rs:197 vs resident_store.h:54 (MAX_RP_ID_LEN 128 vs RES_RP_ID_MAX 64)`:
- **What:** StoredCredential grew to 580 bytes in v11/v12 (asserted at flash_store.rs:410), giving Rust MAX_SLOTS = (4096-240)/580 = 6 resident-credential slots (correctly noted at flash_store.rs:248-251). The C resident store hardcodes RESIDENT_MAX_SLOTS = 8 (resident_store.h:62) and its justification comment (lines 56-62) explicitly claims this matches Rust because 'Rust ... computing MAX_SLOTS = (4096-240)/432 = 8' -- a stale figure: the Rust slot was 432 B at v10 but is 580 B now, so Rust holds 6, not 8. The root cause is an undocumented parity drift from the F4 rp_id work: Rust uses MAX_RP_ID_LEN = 128 (flash_store.rs:197) while C uses RES_RP_ID_MAX = 64 (resident_store.h:54), so the C slot (~500 B) still fits 8 while the Rust slot (580 B) fits only 6. The C comment's stated goal -- 'Aligning the number keeps getCredsMetadata's remaining-count identical across the two ports' -- is now violated.
- **Fix:** Reconcile the two ports: either align MAX_RP_ID_LEN / RES_RP_ID_MAX (and hence the slot size and slot count) so both hold the same number, or set RESIDENT_MAX_SLOTS to the real shared minimum (6) and update the README/parity claim. At minimum, correct the resident_store.h:56-62 comment to the real Rust slot size (580 B) and slot count (6) so it stops citing the dead 432 B / 8-slot math.

The decrypt counterparts (aes_cbc_decrypt at 540, aes_cbc_decrypt_with_iv at 470) DO guard with `ciphertext.len() % 16 != 0 -> None`; the encrypt side is the inconsistent one.
- **Fix:** Add an early guard `if plaintext.len() % 16 != 0 { /* return empty or debug-unreachable */ }` to both encrypt helpers (mirroring the decrypt guards), or pad with `chunk.get(i).copied().unwrap_or(0)`, so the invariant is enforced in release rather than documented-only.

## #33 [INFO/bug/c] C duplicate-key check treats distinct array/map keys with equal element count as duplicates (false-positive dedup)
- **Where:** `c/cbor/pqcbor.c`:155-164 (pqcbor_key_equal), used at 270-279 (map dup-key rejection)
- **What:** pqcbor_key_equal compares two decoded map keys: line 159 returns 0 unless type and arg match, lines 160-162 byte-compare BYTES/STRING payloads, and line 163 returns 1 ('equal') for every other type once type and arg match. For ARRAY and MAP keys, arg is the element/pair COUNT, so two structurally different compound keys that merely share the same count (e.g. array [1,2] vs array [3,4], both arg==2) are declared equal. In the map decode loop (lines 270-279) that makes pqcbor_parse_one reject the second such key as a duplicate (PQFIDO_ERR_CBOR), rejecting input that is actually well-formed and key-distinct under RFC 8949 section 5.6. The element bytes are never consulted for the compound case.
- **Fix:** Make pqcbor_key_equal return 0 (not-equal) for ARRAY/MAP/TAG keys (or recurse element-wise) rather than declaring them equal on matching count alone; CTAP keys are only uint/negint/short text/bytes, so simply restricting the 'return 1' fast-path to UINT/NEGINT/SIMPLE and returning 0 for the compound types is sufficient and safe.

## #35 [INFO/feature/both] getInfo omits remainingDiscoverableCredentials (0x14) field
- **Where:** `crates/firmware/src/ctap2.rs ; c/firmware/src/ctap2.c`:Rust ctap2.rs:1218-1365 (getInfo map ends at 0x10) ; C ctap2.c:1143-1238 (16-entry map, ends at 0x10)
- **What:** Both getInfo encoders stop at key 0x10 (Rust cbor_map! ends at 0x10 maxRPIDsForSetMinPINLength, ctap2.rs:1361-1364; C writes a fixed 16-entry map header `cbor_w_map_header(&w, 16)` covering 0x01..0x10, ctap2.c:1143). CTAP 2.1 sec. 6.4 defines field 0x14 `remainingDiscoverableCredentials` (unsigned, the estimated number of additional discoverable credentials that can be created). The firmware already computes this exact quantity for CredentialManagement getCredsMetadata (Rust credential_management.rs:326 `remaining = max_slots - existing`; C resident_store equivalent), so the value is cheaply available. Surfacing it in getInfo lets platforms (e.g. passkey managers) show remaining-slot capacity without an authenticated credMgmt round-trip and is expected by WebAuthn L3 credential-management UIs.
- **Fix:** Emit key 0x14 = max_slots.saturating_sub(active_resident_count). In C bump the map header to 17 and append after 0x10 (canonical ascending). In Rust add `0x14 => cbor_int!(remaining)` to the map. Note the spec caveat that it MAY be omitted if unknown, so this is optional but low-cost.

## #36 [INFO/feature/both] largeBlobKey extension implemented but absent from getInfo extensions list -- WebAuthn L3 largeBlob discovery gap
- **Where:** `crates/firmware/src/ctap2.rs ; c/firmware/src/ctap2.c`:Rust ctap2.rs:1236-1241 (extensions array) and 1227-1235 (comment justifying omission) ; C ctap2.c:1153-1158 (extensions array)
- **What:** Both ports implement the `largeBlobKey` extension end to end -- MakeCredential parses it and bakes the requested bit into the credentialID (Rust ctap2.rs:1681-1689,1996; C ctap2.c:453), and GetAssertion/MakeCredential return the 32-byte key as top-level response field 0x05/0x07 (Rust ctap2.rs:2147-2173; C ctap2.c:623-647) -- and getInfo advertises the `largeBlobs` option (true) plus 0x0b maxSerializedLargeBlobArray. The Rust comment (ctap2.rs:1227-1235) explains this is an intentional Chrome-compat hedge. - **Fix:** Once the Chrome compatibility concern noted in ctap2.rs:1227-1235 is re-validated, add `largeBlobKey` to the 0x02 extensions array in both ports (canonical length-then-lex: 12 chars, sits with minPinLength).
